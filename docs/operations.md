# バックアップ・復旧とアップデート

## SQLiteを整合性のある状態で保存する

このCompose環境はSQLiteと添付ファイルを同じ永続ボリュームに保存します。書込み中のDBファイルだけをコピーすると不完全なバックアップになるため、停止してデータ全体を取得します。

```sh
mkdir -p .runtime/backups
docker compose stop kanboard
docker compose cp kanboard:/var/www/app/data .runtime/backups/data
docker compose start kanboard
```

プラグインコードと設定も別途保存してください。保存先はGitの対象外です。既存バックアップを上書きしないよう、運用時は日時ごとのディレクトリを作成します。Composeの古い実装で `compose cp` が使えなければ、`docker compose ps -q kanboard` でコンテナIDを確認して `docker cp` を使います。

## 復旧する

停止したインスタンスと現状のバックアップを残し、新しい分離環境へ保存した `data/` と同じバージョンのプラグインを配置します。DB・添付の所有者をコンテナのnginxユーザーに合わせ、起動後に `getTask`、`getAgentContext`、履歴件数、添付のダウンロードを確認します。確認後に接続先を切り替えてください。

削除済みタスクの履歴を回収する場合、管理者はバックアップDBの `agent_memory_entries` を `original_task_id` と `project_id` で調べます。`task_id IS NULL` は削除により切り離された記録です。最新コンテキストは `agent_memory_contexts` にも残り、`entry_id` で元の履歴へ関連付けられます。作業ログ・判断の現在内容と削除状態は `agent_memory_messages`、編集・削除の変更前後は `agent_memory_changes` に保存されます。これらも復旧・バックアップ対象に含めます。画面の削除は非表示化であり、原文・変更履歴の物理消去ではありません。

元のタスクIDへ手動で再接続すると、新しい別タスクへ混ざる恐れがあるため行わないでください。

## 無効化・再導入する

通常の手動導入では `plugins/AgentMemory` を `plugins/` の外へ移動します。Composeでは停止後に該当のマウントを外して再起動します。標準DB・標準機能は維持され、追加テーブルは保持されます。再導入時は同じフォルダー名を使用し、必要なマイグレーションが実行された後で履歴を再確認します。

`plugin_schema_versions` だけを削除しないでください。テーブルが残ったまま初回マイグレーションが再実行されます。プラグインのWebアンインストーラーも追加テーブルを消しません。完全消去が必要な場合は管理者がバックアップ・保存方針を確認したうえで別途対応します。

## アップデートする

現在は1.2.55のみを検証対象とします。新バージョンは別環境で、標準テストとこのリポジトリのテストを実行してから切り替えます。特に `task/show` の2つのフック、ユーザーAPI認証、プロジェクト権限、タスク削除時の外部キー、SQLiteマイグレーションを確認してください。失敗した場合は旧イメージとアップデート前DBの両方を復元します。

SQLite以外ではプラグイン機能を登録しません。別DBへ移行する前に、履歴の移行実装と検証が必要です。プラグインから標準テーブルや既存設定を書き換えることはありません。

公式Dockerイメージは起動時に `plugins/` の所有者を変更するため、読取り専用マウントに対して `chown: Read-only file system` が出ます。この構成では意図した制限で、PHPからの読取りとプラグイン動作には影響しません。

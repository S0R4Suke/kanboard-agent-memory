# プロジェクトを固定して記録する

複数のKanboard環境がある場合は、ブラウザで開いているURLから保存先を選ばず、プロジェクト専用設定と `examples/workspace.py` を使います。設定が見つからない、期待するプロジェクト名と一致しない、タスクが別プロジェクトに属する場合は停止します。同名プロジェクトの作成や別ポートへの接続は行いません。

## ローカル設定

`.runtime/workspace.json` を作ります。このディレクトリはGit対象外です。URL・ID・名前は対象環境で確認した値に置き換えます。

```json
{
  "url": "http://127.0.0.1:8088/jsonrpc.php",
  "project_id": 2,
  "project_name": "YOUR_PROJECT_NAME",
  "credentials_file": "credentials.json"
}
```

認証情報のファイルは `username` と `api_token` を持つJSONとし、POSIX環境では権限を600にします。相対パスは設定ファイルの場所が基準です。値を会話、チケット、コマンド引数、Gitへ貼り付けないでください。

この入口はPython標準ライブラリだけで動作します。作成の直列化にはPOSIXファイルロックを使うため、ローカルのmacOS／Linux向けです。Kanboardプラグイン自体への実行時依存追加はありません。

```sh
# 既存の開いた・閉じたタスクを含めて検索する
python3 examples/workspace.py searchTasks '{"query":"status:all 対象の仕事"}'
# task_idは検索した実際の番号に置き換える
python3 examples/workspace.py resume '{"task_id":123}'
```

`resume` は標準タスク、現在コンテキスト、現在表示される作業ログ・判断、詳細履歴、カラム・スイムレーンを返します。履歴は100件ずつです。`has_more=true` の場合は、返された `next_after_id` を指定して `getAgentEntries` / `getAgentMessages` で続きを取得します。最初の100件だけで全履歴を読んだと扱わないでください。

## 記録するタイミングと場所

- 作業開始：既存チケットを検索し、目的・完了条件・記憶を取得する。対応が不明なら推測で起票・追記しない。
- 重要な進展：`appendAgentEntry` の `work_log` に、実施した内容と結果を短く残す。
- 人間の判断：人間が採用・却下・承認した内容だけを `decision` に残す。判断者・分かる範囲の理由を記載し、AIの推奨案だけで埋めない。
- 技術的な根拠：必要な検証結果、失敗した試行、参照先を `history` に残す。生の実行ログを大量に貼らない。
- 中断・委任・終了：`updateAgentContext` で現状・確定事項・未解決事項・次の行動・制約を更新し、カラムと整合させる。委任先へチケットIDと担当範囲を渡す。

本文は目的・範囲・完了条件の置き場とし、日々の進展を本文にだけ追加する運用にしません。相談だけで仕事を確定していない場合は、起票を強制しません。既存の承認・公開手順は維持します。Kanboardへの記録を本番操作の承認と解釈してはいけません。

書込み例のJSONをローカルファイルへ保存し、`@ファイル名` で渡します。新しい追記ごとにUUIDなどの `request_id` を作り、再送では同じファイルとキーを使います。

```sh
python3 examples/workspace.py appendAgentEntry @work-log.json
python3 examples/workspace.py updateAgentContext @context.json
```

本文の型、`expected_revision`、人間の判断のフィールドは [API仕様](api.md)に従います。コンテキストは全文置換です。再取得せずに版番号を推測したり、残したい項目を省いたりしないでください。

## 書込みと再試行

書込み後の応答には、標準タスクと該当する記憶の読み戻し結果が入ります。呼出側は、意図した本文・版・カラム・スイムレーン・開閉状態と合うことを確認してから「記録済み」と報告します。書込みが成功しても読取りに失敗した場合は未確認として停止します。複数コマンド間の保存は原子的ではありません。

報告するチケットURLは、設定した接続先から作る `canonical_task_url` を使います。標準APIの `task.url` はサーバー側のURL設定によってポート等が異なる場合があるため、そのまま正本のリンクとみなしません。

`createTask` は一意な `reference` が必須です。同じ設定を使うローカルCLI同士は作成処理を直列化し、再試行時は同じreferenceのタスクを照合します。内容が違えば停止します。標準APIにreferenceの一意制約はないため、別クライアント・別ホストとの同時作成まで保証するものではありません。

タスクの削除、プロジェクトの作成・移動などは、この入口では提供しません。標準機能は維持されますが、通常の記録で誤って別プロジェクトへ書かない範囲に限定しています。権限を代替する仕組みではなく、サーバー側の標準認証・認可も適用されます。

## 指示ファイルへ組み込む

作業するリポジトリの指示ファイルへ、実際の設定パス、CLIパス、この手順への参照を短く記載します。既存のworktreeにも同じ設定先を明示し、作業中のチャットは次の作業前に指示を再確認します。設定しただけで全ての既存チャットが自動的に読み直すとは扱いません。

Codexでの指示ファイルの適用範囲は [OpenAI公式のAGENTS.md説明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)を参照してください。特定エージェントの会話を監視する実装は不要です。最後に別セッションから `resume` を実行し、元の会話なしで次の行動を説明できることを確認します。
